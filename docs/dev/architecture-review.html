Strong 1 — extractDirectives called twice in convertFile src/index.js:65–70

Files

src/index.js

Problem

convertFile calls extractDirectives(md) at line 65 just to get cfg.outputFilename for the output path. Then it calls convert(md, …), which calls extractDirectives a second time internally. The markdown is parsed for directives twice per conversion. This is a shallow seam: the function that owns I/O (convertFile) needs information that only the deeper convert function computes — so it reaches in and computes it early, then throws the result away.

The deeper risk: the two calls must always agree. Any stateful directive or a future change that makes parsing non-idempotent silently produces two different config objects. There is no test that catches this divergence.

Solution

Have convert() return outputFilename (already computed from cfg inside it) in its result object alongside buffer, warnings, and meta. convertFile then resolves the output path from the single conversion result — one parse, one source of truth.

Before — two parses

convertFile
extractDirectives ①→cfg.outputFilename
convert(md)
extractDirectives ②→cfg + vars + header + footer

① and ② must always agree — no guarantee.

After — single parse

convertFile
convert(md) → { buffer, outputFilename, warnings, meta }
extractDirectives ①→cfg + vars + header + footer + outputFilename

One parse. convertFile just uses the result.

Benefits

  • Locality: all directive-parsing knowledge lives in one place (inside convert). convertFile becomes a thin I/O wrapper with no config knowledge.
  • Leverage: future callers of convert() get the resolved output filename for free — useful for CLI tools or programmatic use where the caller wants to know what the file would have been named.
  • Testability: a test for the output filename now only needs to call convert() — no file I/O, no convertFile.

Code sketch

// src/index.js — convert() returns outputFilename
export async function convert(md, opts = {}) {
  const { configYaml, docYaml, header, footer } = extractDirectives(md);
  const cfg = buildConfig(configYaml, configOverrides);
  // …
  const { buffer, warnings, meta } = await buildDocument(…);
  return { buffer, warnings, meta, outputFilename: cfg.outputFilename };
}

// convertFile becomes a thin wrapper
export async function convertFile(inputPath, opts = {}) {
  const md = readFileSync(inputPath, 'utf8');
  const { buffer, warnings, meta, outputFilename } = await convert(md, { … });
  const stem = basename(inputPath).replace(/\.[^.]+$/, '');
  const outputPath = opts.output ?? join(dirname(inputPath), (outputFilename || stem) + '.docx');
  writeFileSync(outputPath, buffer);
  return { outputPath, warnings, meta };
}
Worth exploring 2 — PNG utilities buried inside src/mermaid.js src/mermaid.js · src/renderer/image.js

Files

src/mermaid.js, src/renderer/image.js

Problem

src/mermaid.js bundles three distinct capabilities: (a) mermaid-to-PNG rendering (mmdc subprocess, puppeteer config, Chrome detection), (b) PNG/JPEG dimension reading (pngDims), and (c) tall-image slicing (sliceTall). The last two are pure image utilities with no dependency on mermaid at all.

The naming confusion shows up immediately: src/renderer/image.js imports pngDims from ../mermaid.js. A reader following the module graph sees an image renderer depending on a mermaid renderer — a misleading signal. Apply the deletion test to pngDims inside mermaid.js: delete it from there and its complexity doesn't vanish — it reappears in callers. But it's misnamed, not misplaced-complexity. The seam is in the wrong place.

Solution

Extract pngDims and sliceTall into src/image-utils.js. mermaid.js imports from there; so does renderer/image.js. Each module now names what it does.

Before — mixed module

src/mermaid.js
renderMermaid pngDims sliceTall
renderer/image.js→ imports pngDims
from mermaid.js

After — clear seams

src/image-utils.js (new)
pngDims sliceTall
src/mermaid.js
renderMermaid
imports from image-utils.js
renderer/image.js→ imports pngDims
from image-utils.js

Benefits

  • Locality: PNG dimension logic and image slicing are in one named place. Bugs in pngDims are found and fixed without touching mermaid rendering.
  • Testability: pngDims and sliceTall can be unit-tested with a fixture PNG buffer, no mermaid subprocess, no puppeteer.
  • Leverage: any future block type that needs image sizing (e.g. embedded SVGs) imports from image-utils, not from an unrelated module.
Worth exploring 3 — parseYaml housed in config.js, imported by the parser layer src/config.js · src/parser/directive.js

Files

src/config.js, src/parser/directive.js

Problem

config.js is the configuration layer — it defines defaults, merges overrides, and returns the fully-resolved config object. But it also houses parseYaml, a general-purpose mini-YAML parser. Because parseYaml lives in config.js, the parser layer module parser/directive.js must import from the config layer — a direction that goes against the natural dependency flow (parser should be below config, not importing from it).

In addition, src/index.js imports parseYaml from config.js inside buildVariables — so three different modules reach into config.js for the YAML parser. Apply the deletion test to parseYaml inside config.js: delete it and the parser/YAML complexity reappears in three callers, not zero. The module is earning its keep — it just lives in the wrong file.

Solution

Extract parseYaml (and the helper get) into src/yaml.js. config.js imports from there; so do directive.js and index.js. The config layer's interface narrows to what it actually owns: config building and variable resolution.

Before — upward dependency

Config layer
config.js parseYaml get resolveVar buildConfig
parser/directive.js↑ imports parseYamllayer violation
index.js↑ imports parseYaml

After — clean layers

src/yaml.js (new, foundation)
parseYamlget
config.js (narrowed)
buildConfigresolveVar
imports from yaml.js ↓
parser/directive.js→imports from yaml.js ↓
index.js→imports from yaml.js ↓

Benefits

  • Locality: bugs in the custom YAML parser are isolated to yaml.js. The config layer and parser layer can both be understood without reading each other.
  • Testability: the existing config.test.js YAML parser tests can be moved to target yaml.js directly with no config ceremony.
  • Leverage: any future module that needs to parse YAML bodies (e.g. a schema validator) imports from one named place.

This is a pure rename/move with no behavior change — a low-risk refactor that pays back in readability.

Speculative 4 — buildDocument as a god function src/renderer/document.js

Files

src/renderer/document.js

Problem

buildDocument is a 229-line function that does: page geometry, heading anchor pre-pass, block-type dispatch, numbered list instance tracking, running header/footer assembly, docx styles definition, and final Packer.toBuffer call. The interface is shallow in one specific sense: it's impossible to test a single block-type render in isolation — every test must call the full document builder and inspect the output buffer.

Apply the deletion test: delete buildDocument and the complexity doesn't spread — the individual block renderers (table.js, code.js, image.js, renderer/mermaid.js) already exist as separate modules. The dispatch loop and document assembly are the things that have no seam.

Why speculative: the existing tests are integration-level and work fine for a library of this size. The friction only bites when you want to test a new block type's output format without building an entire document. At the current scale this is a marginal gain.

Solution sketch

Extract the block dispatch into a renderBlocks(blocks, cfg, ctx, layoutCtx) function that returns the children array. buildDocument handles only geometry, styles, and Packer. Each block renderer is then testable via renderBlocks without a full docx round-trip.

Before — one big function

buildDocument (229 lines)
page geometry anchor pre-pass block dispatch loop numbering state header/footer styles Packer.toBuffer

After — two concerns

renderBlocks(blocks, cfg, ctx, layoutCtx) → Paragraph[]
dispatch loop numbering state
buildDocument → Buffer
page geometry anchor pre-pass calls renderBlocks header/footer styles Packer.toBuffer

Benefits

  • Testability: renderBlocks returns a plain array of docx Paragraph objects — inspectable without unpacking a Buffer.
  • Locality: adding a new block type only touches renderBlocks, not the full 229-line function.

This is worth revisiting when block types grow beyond ~10 or when testing becomes painful. Not urgent today.

Top recommendation: Candidate 1

Fix extractDirectives being called twice in convertFile first. It's the only candidate that introduces a real correctness risk (two parses must agree, with no enforcement), it's a 10-line change with zero behavior change for callers, and the fix simultaneously adds useful information (outputFilename) to the convert() return value.

After that, Candidate 2 (extract PNG utilities) is a clean rename/move — low risk, immediate clarity improvement. Candidate 3 (parseYaml extraction) follows naturally and rounds out the module graph. Candidate 4 is only worth opening if the block dispatch grows substantially.
